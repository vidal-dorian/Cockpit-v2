- **Modifie** : la [012](012-configuration-automatique.md), choix D (Pull requests en écriture, pour G)

## Contexte

La 6.2 (« Préparer pour Claude en un clic ») ajoutera à un repo le skill `/dev-us`, ses agents et un `.mcp.json` : **un seul commit, montré fichier par fichier avant d'être fait, sans rien écraser** (brief §6.1). Le catalogue fera de même plus tard (brief §6.10 : il n'écrase jamais une copie modifiée). Cette tranche construit le mécanisme commun, sans écran : lire ce qui est là, dire ce qui serait fait, puis le faire en un commit, et refuser si le repo a changé entre-temps d'une façon qui compte. Elle est testée contre un faux GitHub.

## Les choix

| # | Question | Décision |
|---|---|---|
| A | La forme ? | Deux fonctions du client GitHub, sur la branche par défaut du repo, avec l'identité de l'installation (jamais celle d'un utilisateur, 011). **`planRepoWrite(installationId, fullName, files)`**, `files` étant une liste `{ path, content }`, rend un **plan** : le commit de départ (`baseSha`) et, pour chaque fichier, `create` (absent : il sera ajouté), `same` (déjà là avec ce contenu : rien à faire) ou `exists` (déjà là avec un **autre** contenu : **jamais écrasé**, le plan donne alors le contenu actuel pour que la 6.2 montre la différence). **Tout ce qui n'est pas un simple fichier** compte aussi comme `exists`, sans contenu : un dossier, un lien symbolique ou un sous-module au chemin, un fichier trop gros pour être lu (GitHub ne rend pas son contenu), et un chemin dont **un dossier parent** n'est pas un vrai dossier (un lien symbolique, un sous-module ou un fichier) : y écrire remplacerait ce parent. **`applyRepoWrite(installationId, fullName, plan, message)`** fait **un seul commit** qui ajoute les fichiers `create`, et rien d'autre. Rien n'est écrit si aucun fichier n'est à créer |
| B | Comment GitHub est-il appelé ? | Lecture : la branche par défaut et son commit, puis, pour chaque fichier, l'arbre Git de son dossier à ce commit (`GET git/trees/<sha>:<dossier>`, qui dit si une entrée est un fichier, un dossier, un lien ou un sous-module), **en descendant depuis la racine** et en ne passant que par des entrées de type dossier : ce que GitHub répond pour le chemin d'un sous-module (404, 422 ou même 200) ne compte jamais ; le contenu d'un simple fichier est lu à ce commit (`GET contents/{path}?ref=<sha>`). Écriture par l'API Git : un arbre sur l'arbre du commit (`POST git/trees` avec `base_tree`, mode `100644`, contenu en UTF-8), un commit qui a ce commit pour parent, puis la branche avancée **sans forcer** (`PATCH git/refs/heads/<branche>`, `force: false`) : GitHub refuse alors tout ce qui n'est pas une avance rapide |
| C | Et si le repo a changé entre le plan et l'écriture ? | `applyRepoWrite` relit chaque fichier `create` au commit de la branche, avec les mêmes règles que le plan, **sauf** si le plan est intact et la branche inchangée (H) : le plan peut venir de loin, il ne fait foi que signé ; s'il est **encore absent** partout, le commit est fait sur le nouveau commit (un push sans rapport ne doit pas bloquer) ; si l'un d'eux est apparu, **refus `repo_changed`**, rien n'est écrit, et l'appelant refait un plan. Si GitHub refuse l'avance de la branche (un autre push au même moment), même refus : on ne réessaie pas en boucle. Les fichiers `same` et `exists` ne sont pas relus : ils ne sont pas écrits |
| D | Quels chemins sont acceptés ? | Relatifs, en `/`, sans segment vide, `.` ou `..`, sans `.git` comme segment (en majuscules ou minuscules), sans caractère de contrôle, 255 caractères au plus ; au plus 50 fichiers et 1 Mio de contenu par plan ; un chemin donné deux fois, ou qui est le dossier d'un autre chemin du même plan, est refusé. Tout autre plan est une erreur de programmation (une exception), pas un refus montré à l'utilisateur : les fichiers viennent du catalogue de Cockpit, pas d'une saisie |
| E | Les autres refus ? | `empty_repo` (le repo n'a aucun commit : GitHub répond 409), `repo_unreachable` (404 : l'App n'y a plus accès), `pull_request_forbidden` (voir G). Les autres erreurs de GitHub remontent telles quelles à l'appelant, comme pour le bilan de santé (013 H) |
| F | Que rend l'écriture ? | `{ commitSha, created: [chemins] }`, plus `pullRequest: { number, url }` quand le commit est passé par une pull request (G). L'historique (`github_effects`) et l'écran viennent avec la 6.2, qui saura pour qui et pourquoi on écrit |
| G | Et si la branche par défaut est protégée ? | Demande de Dorian (2026-10-31) : **une pull request est ouverte**. Quand GitHub refuse l'avance de la branche par défaut pour une protection (403 ou 422 dont le message parle de « protected branch » ou de « rule violation »), le commit déjà fait est posé sur une **nouvelle branche** `cockpit/<7 premiers caractères du commit>` (`POST git/refs`, jamais forcée) et Cockpit ouvre une pull request de cette branche vers la branche par défaut (`POST /pulls`, titre : le message du commit ; corps : la liste des fichiers ajoutés et « Ouverte par Cockpit »). Il faut à l'App **Pull requests en écriture** : la 012 D est modifiée en ce sens pour les nouvelles installations ; une App déjà créée la reçoit à la main (réglages de l'App sur GitHub, puis acceptation sur l'installation). Sans cette permission, GitHub répond 403 à l'ouverture : Cockpit supprime la branche qu'il vient de créer et refuse `pull_request_forbidden`, que la 6.2 expliquera |
| H | Ne rien lire deux fois ? | Demande de Dorian (2026-10-31) : une application optimisée ne relit pas la même chose. **Dans un même appel**, chaque arbre de dossier est lu **une seule fois**, quel que soit le nombre de fichiers qui le traversent (les lectures en cours sont partagées). **Entre le plan et l'écriture**, le plan porte une **signature** (HMAC-SHA256 du commit de départ et de chaque chemin, statut et contenu, avec une clé tirée au hasard au démarrage de Cockpit) : si elle est valide **et** que la branche n'a pas bougé, `applyRepoWrite` ne relit rien. Sinon (branche qui a bougé, plan modifié en route, Cockpit redémarré entre-temps), il relit les fichiers à créer comme en C. Un plan modifié ne peut donc jamais faire écrire par-dessus un fichier, et un plan intact ne coûte aucune lecture de plus |

## Ce qui est repoussé

- L'écran, l'historique, le diff montré à l'utilisateur et le bouton : 6.2.
- Mettre à jour une copie du catalogue **non modifiée** (brief §6.10) : avec le catalogue ; il faudra savoir quelle version a été copiée.
- Les fichiers binaires et les liens symboliques : rien ne les demande.

## Limites connues

- **Un fichier `exists` est laissé tel quel** même s'il n'a qu'une fin de ligne de différence : c'est le prix de « sans rien écraser ».
- **Entre la relecture (C) et l'avance de la branche**, un push peut ajouter un des fichiers : GitHub refuse alors l'avance (elle n'est plus rapide), et le refus est `repo_changed`. Aucun fichier n'est jamais écrasé.
- **La branche par défaut est relue à chaque appel** : après un renommage entre le plan et l'écriture, le commit va sur la nouvelle branche par défaut ; un renommage pendant l'écriture même fait échouer l'avance de la branche (une erreur, rien n'est écrit).
- **Non vérifiable ici** : le statut exact que GitHub rend à un push refusé par une règle de protection (403 ou 422 selon le type de règle) ; les deux mènent à la pull request (G) quand le corps parle de protection.
