## Contexte

Un projet n'a qu'un membre, son propriétaire, garanti par un index unique (008 F). La 064 13.1 a tranché le partage : trois rôles, une invitation par login GitHub dont l'invitant envoie lui-même le lien, l'inscription qui reste ouverte, et l'administrateur qui voit l'activité des comptes sans voir leurs projets.

## Les choix

| # | Question | Décision |
|---|---|---|
| A | Les rôles | `project_members.role` prend quatre valeurs : `owner` (propriétaire, un seul par projet, celui qui l'a importé), `can_launch` (« peut valider et lancer »), `can_validate` (« peut valider »), `read_only` (« lecture seule »). Ils s'emboîtent : chaque rôle a les droits du précédent. **Lecture seule** : tout lire du projet (Kanban, tickets, US, runs, bilan, son historique) ; ses préférences à lui (l'étoile, 073 H ; la case du lanceur cloud, 054 D) restent les siennes. **Peut valider** : en plus, les décisions humaines sur les US (018 : valider, renvoyer, modifier, abandonner) et les tickets (noter une idée, modifier, abandonner un ticket). **Peut valider et lancer** : en plus, lancer, arrêter, relancer et fermer un run, répondre à une question de Claude, mettre une US dans la file ou dans la nuit. **Propriétaire** : tout le reste, soit archiver le projet, gérer ses membres et ses invitations, et tout ce qui écrit dans le repo ou configure le projet (Préparer pour Claude, équipes et agents, configuration Claude, CI / CD et « Demander à Claude » sur un workflow, routines, reprise et figer, branches, changelog). Juger les règles d'une US de reprise (garder, modifier, signaler un bug) est une décision sur une US : **peut valider**. Le serveur refuse le reste en 403 `role`, journalisé `refused` |
| B | Le MCP | Claude agit pour l'utilisateur du jeton : un outil qui écrit demande le rôle du geste humain qui lui correspond. Les outils de lecture : tout membre. `create_ticket` et les outils qui écrivent ou modifient une US : **peut valider**. Démarrer un run ou un lancement (`start_run`, `report_launch`, `finish_launch`) : **peut valider et lancer**. Les rapports d'un run déjà démarré (`report_step`, `report_criterion`, `ask_user`, `link_pull_request`, `finish_run`) restent permis à celui qui l'a lancé, quel que soit son rôle ensuite, même retiré du projet : un run lancé va jusqu'au bout (F). Ceux de la reprise et de la configuration (`submit_code_map`, `submit_findings`, `create_takeover_stories`, `propose_workflow_change`) : **propriétaire**. Un refus rend l'erreur `role`, journalisée comme les autres refus du MCP |
| C | L'accès GitHub de l'invité | Une installation de l'App appartient au compte qui possède le repo : celle de l'invité ne peut pas couvrir le repo d'un autre, comme la 064 13.1 D le demandait. **Cockpit vérifie donc que l'invité a lui-même accès au repo sur GitHub** : à l'acceptation, une autorisation GitHub (comme la création depuis un modèle, 068 D, retour par `/api/auth/callback` reconnu à son `state`) donne un jeton de l'invité, utilisé une fois pour lire le repo puis oublié. Sans accès : « Tu n'as pas accès à `owner/repo` sur GitHub. Demande à `@proprio` de t'y ajouter comme collaborateur, puis rouvre ce lien. » Les écritures sur GitHub restent celles de l'App (son installation sur le repo), jamais un jeton personnel du propriétaire |
| D | Inviter (S48) | Réglages › **Membres**. « Inviter quelqu'un » : un champ **@login GitHub**, un projet parmi ceux dont l'utilisateur est propriétaire (une puce par projet actif, une seule choisie), un rôle (lecture seule, peut valider, peut valider et lancer ; peut valider par défaut), « Créer le lien d'invitation ». Cockpit lit le compte sur GitHub (`GET /users/{login}`) et garde son identifiant numérique : seul ce compte pourra accepter, même renommé. Le lien `/invitations/<secret>` est montré **une seule fois**, avec « Copier » ; le secret est gardé haché (015). Une invitation vaut **7 jours** et ne sert qu'une fois. Refus en français : login inconnu sur GitHub, déjà membre, déjà invité sur ce projet, c'est toi |
| E | Accepter | `/invitations/<secret>` demande la connexion si besoin (retour sur le lien), puis montre « `@proprio` t'invite sur `owner/repo`, rôle : peut valider » et « Accepter ». Accepter vérifie le compte (C) et l'accès GitHub (C), ajoute le membre et efface l'invitation. Une invitation expirée, déjà servie, annulée ou destinée à un autre compte dit la même chose, sans détail : « Ce lien d'invitation n'est plus valable. Demande-en un nouveau. » L'invité trouve le projet dans « Tous les projets », marqué « partagé par `@proprio` · <rôle> » |
| F | La liste des membres (S48) | Phrase d'état : « N personnes voient tes projets partagés. » / « Chacune ne voit que ce que tu lui partages. » (aucune : « Personne ne voit tes projets. » / « Invite quelqu'un sur un de tes projets. »). Liste : toi d'abord (« propriétaire · N projets »), puis une ligne par membre et par projet (« `<nom>` · `<projet>` · `<rôle>` · actif il y a 1 h », d'après sa dernière connexion) avec « Modifier » (changer le rôle, ou « Retirer » après confirmation), puis une ligne par invitation en attente (« @login · `<projet>` · invitation créée il y a 2 j ») avec « Nouveau lien » (l'ancien ne vaut plus rien) et « Annuler ». Retirer un membre, ou le passer sous « peut valider et lancer », retire aussi ses US de ce projet de sa file et de sa nuit ; un run déjà lancé continue (B) |
| G | Ce que l'invité voit ailleurs | Les écrans existants se fondent déjà sur l'appartenance (accueil, Kanban, recherche, notifications) : un projet partagé y entre tel quel. Le projet porte son `role` dans ce que rend le serveur ; sur la page de l'US, le Kanban et l'onglet Santé, les boutons d'un geste que le rôle ne permet pas sont masqués. Partout ailleurs, le refus du serveur s'affiche : « Ton rôle sur ce projet ne le permet pas. » |
| H | L'administrateur | Il ne voit pas les projets des autres (inchangé). Réglages › Instance, la liste des utilisateurs (012 G) gagne pour chacun la **dernière connexion** et le **nombre de projets** dont il est membre |
| I | L'historique | Créer, renouveler, annuler, accepter une invitation, changer un rôle et retirer un membre sont des actions journalisées (010), sur le projet, sans le login de l'invité dans `args` (010 D : des identifiants, pas de données personnelles) |
| J | L'import | Inchangé : un repo déjà suivi est refusé avec le message neutre de la 008 (« Ce repo est déjà suivi dans Cockpit ») ; on y entre par une invitation |

## Ce qui ne change pas

- L'inscription reste ouverte (012 G, 064 13.1 C) : l'invitation sert à partager un projet, pas à entrer dans Cockpit.
- Aucun e-mail : Cockpit ne fait que créer le lien.
- Le propriétaire ne change pas : pas de transfert de propriété dans cette tranche.

## Ce que le code a précisé (tranche 13.1)

- **Migration `0047`** : table `project_invitations` (`project_id`, `github_id`, `login`, `role`, `secret_hash` unique, `expires_at`, `created_at` ; index unique `(project_id, github_id)`), colonne `users.last_login_at` (posée à chaque connexion, nulle avant), `project_members.role` à quatre valeurs (`owner`, `can_launch`, `can_validate`, `read_only`, par `CHECK`), l'index « un membre par projet » remplacé par un index unique `project_members_owner_idx` sur `project_id` où `role = 'owner'`. Une invitation ne porte pas `owner`.
- **Le rôle** : `memberProject(db, userId, projectId, min = "read_only")` (`projects.ts`) rend le projet avec son `role`, `undefined` pour un non-membre (404) et lève `RoleRefused` pour un rôle sous `min`. `onError` (`app.ts`) la rend en 403 `{ error: "role" }` et journalise `refused_role` sur le projet (sans `args`) ; le MCP la journalise comme ses autres refus. Toute route qui écrit passe son rôle ici (`memberStory` et `memberTicket` le prennent aussi).
- **Les routes** (`members.ts`), propriétaire du projet pour les quatre premières : `POST /api/projects/:id/invitations` (`{ login, role }` → 201 `{ invitation, url }` ; 404 `unknown_login`, 409 `self`, `already_member`, `already_invited`, `project_archived`, 502 `github_unavailable`, 400 sur un corps invalide), `POST /api/invitations/:id/renew` (→ `{ url }`), `DELETE /api/invitations/:id`, `PATCH /api/projects/:id/members/:userId` (`{ role }`) et `DELETE` du même chemin (409 `owner` sur le propriétaire, 404 si le membre est inconnu) ; `GET /api/members` (les projets de l'utilisateur dont il est propriétaire, leurs membres et invitations en attente, `me`) ; `GET /api/invitations/:secret` (`{ invitation: { owner, fullName, role } }`) et `POST /api/invitations/:secret/accept` (`{ authorizeUrl }`) pour l'invité, qui répondent 404 `invalid_invitation` dans tous les cas où le lien ne sert pas (expiré, servi, renouvelé, autre compte, projet archivé). Les rôles acceptés sont `read_only`, `can_validate`, `can_launch`. Actions journalisées : `create_invitation`, `renew_invitation`, `cancel_invitation`, `accept_invitation`, `change_member_role`, `remove_member` (`args` : des identifiants et le rôle).
- **Le retour de l'invitation** : `POST …/accept` pose un cookie `cockpit_invitation_state` (`<state>.<secret>`, 10 minutes) et rend l'adresse d'autorisation GitHub ; `invitationReturn` est essayé par `/api/auth/callback` avant le retour du modèle (068). Il échange le code, lit le repo avec le jeton de l'invité (oublié ensuite), supprime l'invitation (c'est la suppression qui tranche : un second retour ne trouve rien) et ajoute le membre, puis redirige vers `/projets/:id`. Les échecs reviennent sur `/invitations/<secret>?erreur=` `lien-invalide`, `annulee`, `sans-acces` ou `github-injoignable`.
- **Retrait et changement de rôle** : retirer un membre, ou le passer à un rôle autre que `can_launch`, supprime ses lignes de file (`queue_items`) et de nuit (`night_items`) de ce projet, dans la même transaction.
- **Un run lancé va jusqu'au bout** : les rapports d'un run (`ownRun`, `runs.ts`) ne demandent que d'en être l'auteur (`runs.user_id`), pas un rôle ni même l'appartenance ; arrêter, relancer et fermer demandent `can_launch`.
- **Les webhooks** : les entrées d'historique d'une livraison vont au propriétaire du projet (`role = 'owner'`), pas à un autre membre.
- **L'administrateur** : la liste des utilisateurs rend `lastLoginAt` et `projects` (le nombre, jamais lesquels).
- **Le web** : `roles.ts` (`ROLE_LABELS`, `atLeast`, `refusedError` : « Ton rôle sur ce projet ne le permet pas. » sur un 403 `role`) ; `Members.tsx` (Réglages › `membres`) et `Invitation.tsx` (`/invitations/:secret`) ; les projets rendent `role` et `sharedBy` (« partagé par `@proprio` · rôle » dans « Tous les projets ») ; les boutons d'un geste que le rôle ne permet pas sont masqués (page de l'US, Kanban, Santé, tickets, file et nuit).

## Limites connues

- **Un seul projet par invitation** : S48 montre des puces, une seule est choisie ; inviter sur deux projets fait deux liens.
- **L'accès GitHub n'est lu qu'à l'acceptation** : un collaborateur retiré sur GitHub plus tard reste membre dans Cockpit jusqu'à ce que le propriétaire le retire.
- **Pas de « Quitter le projet »** pour un membre : le propriétaire le retire.
- **Refus journalisés sous une action générique** : un refus de rôle est écrit `refused_role`, pas sous le nom du geste tenté.
- **Un corps mal formé répond 400 avant 403** sur les routes qui lisent leur corps avant de vérifier le rôle.
- **Un membre en lecture seule peut rafraîchir une PR**, ce qui peut avancer une US comme le fait le webhook (038).
- **Une invitation expirée bloque encore une nouvelle invitation** du même compte sur ce projet (`already_invited`) tant que le propriétaire n'a pas cliqué « Nouveau lien » ou « Annuler ».
- **Le rôle est lu à chaque requête** : un changement vaut tout de suite, et les US en file ou dans la nuit du membre sont retirées (F), pas relancées.
- **Écarts avec S48** : « @login GitHub » à la place du champ e-mail ; « Nouveau lien » et « Annuler » à la place de « Renvoyer ».
