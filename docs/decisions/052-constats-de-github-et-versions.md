## Contexte

La 007 J : Cockpit lit ce que GitHub sait déjà, sans crédits Claude (alertes Dependabot, code scanning, secret scanning), et les dates de fin de vie des runtimes sur [endoflife.date](https://endoflife.date). Claude ajoute ce que ces outils ne voient pas, comme un plan de migration (`upgrade-advisor`). Démo : une alerte Dependabot apparaît dans les constats ; Node 20 en fin de vie est signalé sur la carte.

Pour lire les alertes, l'App a besoin de trois permissions en lecture de plus. **Aucune API ne modifie les permissions d'une App existante** (012) : quelqu'un les coche sur GitHub, puis chaque compte qui a installé l'App les approuve. Le 2026-11-08, Dorian a choisi que **Cockpit guide** : le manifeste demande les nouvelles permissions pour une nouvelle App ; pour une App existante, une ligne du bilan de santé et une ligne sur l'écran des constats donnent le lien et ce qu'il faut cocher ; tant que ce n'est pas fait, Cockpit dit que les alertes sont indisponibles.

## Les choix

| # | Question | Décision |
|---|---|---|
| A | Les permissions ? | Le manifeste de l'assistant (012 D) ajoute `dependabot_alerts`, `security_events` (le nom GitHub des alertes de code scanning) et `secret_scanning_alerts`, en lecture, et les événements `dependabot_alert`, `code_scanning_alert` et `secret_scanning_alert`. Une App créée après R6 n'a rien à faire à la main |
| B | Savoir ce qui manque ? | Une sixième ligne du bilan de santé, **« Alertes GitHub »** (clé `github_alerts`). Cockpit lit les permissions de l'App (`GET /app`) et celles de l'installation du projet (`GET /app/installations/{id}`), en parallèle et avec le jeton de l'App. Il compare les trois permissions de A. **`app_missing_permissions`** : l'App ne les demande pas. La ligne dit quoi cocher dans « Permissions & events » de l'App, avec le lien « Modifier l'App sur GitHub ↗ » (la page des permissions de l'App). **`installation_not_approved`** : l'App les demande, mais l'installation ne les a pas encore. La ligne dit « GitHub attend ton accord pour les nouvelles permissions de l'App », avec le lien « Approuver sur GitHub ↗ » (le `html_url` de l'installation). `unknown` quand GitHub ne répond pas |
| C | Lire les alertes ? | **« Actualiser »** sur l'écran des constats : `POST /api/projects/:id/findings/refresh`, réservé aux membres, sur un projet actif. Cockpit lit les alertes **ouvertes** des trois outils, en parallèle, 100 par page, **10 pages au plus par outil** ; une page de moins de 100 alertes est la dernière. La réponse dit, pour chaque outil, `ok`, `no_permission` (l'installation n'a pas la permission, lue comme en B : l'outil n'est alors pas lu) ou `disabled` (l'installation a la permission mais GitHub répond 403 ou 404 : l'outil n'est pas activé sur ce repo). Elle dit aussi combien de constats sont créés, mis à jour et fermés. **Puis par webhook** (les trois événements de A) : une alerte reçue est traitée comme à la lecture. L'historique garde l'appel avec les comptes (`refresh_github_alerts`) |
| D | Une alerte en constat ? | Toutes de type `security`, `source = github`. **Dependabot** : titre « `<paquet>` : `<résumé de l'avis>` », gravité de l'avis (`moderate` compte comme `medium`), texte avec l'identifiant GHSA ou CVE, l'écosystème, les versions touchées, la première version corrigée, le manifeste et le lien vers l'alerte ; pas de lignes citées (GitHub ne les donne pas). **Code scanning** : titre de la règle, gravité de sécurité de la règle, sinon `error` → `high`, `warning` → `medium`, `note` → `low` ; texte avec l'outil, la règle, le message et le lien ; les lignes de la dernière occurrence, à son commit. **Secret scanning** : titre « Secret exposé : `<type>` », gravité `critical` ; texte avec le type et le lien ; les lignes de **son premier emplacement** dans un commit (un appel de plus par alerte de secret). **Jamais la valeur du secret** : Cockpit ne copie que les champs qu'il nomme, jamais le champ `secret` (principe 5 du brief). La livraison d'un webhook `secret_scanning_alert` porte la valeur dans `alert.secret` : **la route des webhooks retire ce champ avant d'enregistrer la livraison** (024), la valeur n'est donc écrite nulle part. Le texte venu de GitHub passe par le rendu Markdown sûr de la 051 |
| E | Sans doublon ? | Une alerte est reconnue par son outil et son numéro : `github_alert_type` (`dependabot`, `code_scanning`, `secret_scanning`) et `github_alert_number`, uniques par projet. Une alerte relue met à jour le titre, le texte, la gravité et les lignes de son constat, **jamais son statut** : un constat trié reste trié |
| F | Une alerte fermée sur GitHub ? | Corrigée ou rejetée sur GitHub, elle n'est plus à trancher dans Cockpit : `github_closed_at` est daté, et le statut ne bouge pas. Un constat fermé sur GitHub sort de la liste à trancher ; il apparaît dans le filtre « Rejetés », avec « fermée sur GitHub ». **Rouverte** sur GitHub, l'alerte revient à trancher (`github_closed_at` remis à nul). À « Actualiser », un constat GitHub encore ouvert dont l'alerte n'est plus dans la liste est fermé, **seulement si son outil a été lu** (`ok`). Un constat en ticket ou fermé ne se tranche plus (409 `not_open`, 051) |
| G | Le stockage ? | Migration de `findings` : `source` accepte `github`. Trois colonnes : `github_alert_type`, `github_alert_number` et `github_closed_at`. Index unique `(project_id, github_alert_type, github_alert_number)`. `CHECK` : `source = 'github'` si et seulement si le type et le numéro sont remplis. `commit_sha` devient facultatif pour un constat GitHub seulement, par un `CHECK` (une alerte Dependabot n'a pas de commit). Les lignes citées vont dans `code_sources`, comme pour Claude |
| H | L'écran des constats ? | Le bouton **« Actualiser »** est en haut à droite. Les lignes GitHub disent leur source : « dépendance · GitHub », « faille · GitHub », « secret · GitHub ». Après « Actualiser », si un outil est `no_permission`, une ligne grise reprend le texte et le lien de B. Si un outil est `disabled`, une ligne grise dit lequel n'est pas activé sur le repo. Les filtres gagnent **« Versions »** (entre « Failles » et « Architecture », comme S44). Le panneau d'un constat GitHub a en plus le lien « Voir l'alerte sur GitHub ↗ ». « En faire un ticket » met ce lien dans le ticket |
| I | La fin de vie ? | `GET /api/projects/:id/versions`, réservé aux membres. Pour chaque runtime de la carte (043), Cockpit cherche le produit sur `https://endoflife.date/api/v1/products/<produit>`. Le produit est le nom du runtime en minuscules, ou un alias (`node` → `nodejs`, `.net` → `dotnet`, `vue.js` → `vue`, `postgres` → `postgresql`, `spring boot` → `spring-boot`, `ruby on rails` → `rails`). La version est le premier nombre trouvé, avec sa décimale s'il en a une (« ^18.3.1 » → « 18.3 »). Le cycle est la release qui porte ce nom, sinon celle du nombre seul. État : **`eol`** (`isEol`, ou `eolFrom` passée), **`soon`** (`eolFrom` dans les 6 mois, 007), `ok`, ou `unknown` (produit ou cycle inconnu, ou site injoignable). Le cache est en mémoire, 24 heures par produit, un « inconnu » compris ; une panne n'est pas gardée en cache. Chaque lecture a 5 secondes au plus, et Cockpit fait une lecture par produit, pas par runtime. Rien n'est stocké (007 : « à l'affichage ») |
| J | Où la voir ? | **Sur la carte** (S41) : la ligne des runtimes écrit « php 7.4 · fin de vie depuis nov. 2022 » ou « node 18 · fin de vie en avr. 2025 », en mots, sans couleur de plus (045 C). **Dans les constats** : un runtime `eol` ou `soon` est une ligne de la liste (filtres « Tous » et « Versions »), « `<nom> <version>` n'est plus maintenu » ou « … ne sera plus maintenu en `<mois année>` ». Sous le titre : « version · fin de vie depuis nov. 2022 · endoflife.date ». Le même runtime à la même version dans plusieurs sous-projets (node 20 dans le web et dans l'API) ne fait **qu'une ligne** ; son panneau nomme chaque sous-projet et montre la ligne du manifeste de chacun. Les constats `upgrade` de Claude sont des constats comme les autres, sous « Tous » et « Versions », avec le mot « mise à jour ». La gravité est « haute » pour `eol` et « moyenne » pour `soon`. Ce n'est pas un constat : la ligne ne compte pas dans « N constats », ne passe jamais en rouge et ne se trie pas. Un clic ouvre le panneau : le runtime, son sous-projet, la date, la ligne du manifeste (`CodeView`), et **« Demander un plan à Claude »**, qui ouvre la fenêtre d'analyse avec la case « Versions » |
| K | `upgrade-advisor` ? | Un agent de plus au catalogue (`sonnet`, modifiable comme les autres, 051 L). Il part des runtimes et des dépendances du repo et des constats déjà connus (`list_findings`, alertes GitHub comprises), et dépose des constats **`upgrade`** par `submit_findings`, avec le gabarit de la 007 : de quelle version à laquelle, la date de fin de vie, les ruptures connues, l'effort, et la ligne du manifeste citée. `submit_findings` accepte maintenant `upgrade`. Le skill `/analyser` gagne le mot `versions`, et la fenêtre d'analyse la case **« Versions »**. « Préparer pour Claude » et « Mettre à jour » l'écrivent ; `catalog/history.json` est régénéré |
| L | « Mises à jour automatiques » ? | Une septième ligne du bilan (clé `updates`) : verte s'il y a `.github/dependabot.yml` ou `.yaml`, ou une configuration Renovate (`renovate.json`, `renovate.json5`, `.renovaterc`, `.renovaterc.json` à la racine, `renovate.json` ou `renovate.json5` dans `.github`). Pour ça, Cockpit lit `<sha>:.github` (non récursif) dans la même vague que `.github/workflows` : un appel de plus, pas de vague de plus (013 A). **Sa correction**, « Ajouter .github/dependabot.yml », montre le fichier puis l'écrit, comme « Préparer pour Claude » (026 : un commit sur la branche par défaut, ou une PR si elle est protégée). Elle passe par `GET /api/projects/:id/dependabot/plan` et `POST /api/projects/:id/dependabot/apply`. Le fichier a une entrée par écosystème trouvé, avec une mise à jour chaque semaine. Les écosystèmes viennent des manifestes de la racine et de ceux de la carte : `package.json` → `npm`, `composer.json` → `composer`, `requirements.txt`, `pyproject.toml` ou `Pipfile` → `pip`, `Gemfile` → `bundler`, `go.mod` → `gomod`, `Cargo.toml` → `cargo`, `pom.xml` → `maven`, `build.gradle(.kts)` → `gradle`. S'y ajoute `github-actions` s'il y a des workflows. Le dossier de chaque entrée est celui du manifeste. Sans aucun écosystème : 409 `no_ecosystem` |

## Ce qui est repoussé

- **Un bandeau sur tout Cockpit** quand l'App manque de permissions : la ligne du bilan et celle de l'écran des constats suffisent pour l'instant.
- **Le lien vers une App qui appartient à une organisation** : comme pour `pull_request_forbidden` (026 G), le lien suppose une App créée par un compte personnel (`github.com/settings/apps/<slug>`).
- **Regrouper les alertes d'un même paquet** (S44 écrit « symfony/http-kernel 5.4.2 : 2 alertes Dependabot ») : la 007 veut un constat par alerte, pour trier chacune et éviter les doublons par numéro. La décision l'emporte sur la maquette.
- **La source de la ligne de fin de vie** : S44 écrit « GitHub ». La date vient d'endoflife.date, et c'est ce que la ligne dit.
- **Écrire une configuration Renovate**, et **la fin de vie des dépendances** autres que les runtimes de la carte.
- **Les autres emplacements** d'un secret : seul le premier est cité, le lien de l'alerte montre le reste.

## Limites connues

- **Tant que l'App n'est pas modifiée et approuvée, rien n'est lu** : la ligne du bilan le dit. Une installation par compte : chaque compte approuve pour ses repos.
- **Une alerte Dependabot ne cite pas de ligne** : le texte nomme le manifeste.
- **Plus de 1 000 alertes ouvertes** pour un outil : les suivantes ne sont pas lues à « Actualiser », mais le webhook les apporte quand elles changent.
- **Le produit d'endoflife.date est deviné** à partir du nom du runtime : un nom inconnu donne « inconnu », sans signal.
- **Le cache de la fin de vie est en mémoire** : il s'ajoute aux choses à passer en base pour plusieurs instances ([architecture](../architecture.md), « Montée en charge »).
